MCP July 2026 Release Candidate — Stateless Protocol, Extensions Graduate to First-Class The Model Context Protocol working group published the July 28, 2026 Release Candidate on June 8, 2026, pivoting the spec's core architecture from a stateful session model to a stateless transport with optional stateful applications layered on top. The stateless topology means any MCP client can route to any server instance with no session store required, which removes the sticky-session constraint that blocked horizontal scaling of MCP servers behind load balancers. Server-to-client requests are restructured: previously the server could push to the client only through a sampling callback; the RC elevates this to a general server-initiated request primitive. The Extensions framework is now first-class — new capabilities ship as opt-in extensions and stabilize there before, if ever, moving into the core spec. The MCP Apps extension (SEP-1865) lets servers ship interactive HTML interfaces rendered in sandboxed iframes, and the Tasks extension graduates from experimental to a named extension. Three previously experimental features are deprecated under the new feature lifecycle policy (SEP-2577). Full JSON Schema 2020-12 validation for tools is now required rather than recommended. Technical depth angle: The stateless protocol redesign eliminates the session-store requirement by moving all session state to the client side, with each request carrying full context. This enables a horizontally scalable server topology where a single load-balanced IP can dispatch to any server replica without sticky sessions. Server-initiated requests add a server_request primitive to the JSON-RPC layer, letting MCP servers push prompts, resource updates, or tool results without a client poll. The Extensions framework uses a versioned namespace per extension, so operators can pin to a specific extension version independently of the core spec version. MCP Apps (SEP-1865) uses a server-authored HTML payload rendered in a sandboxed iframe with a controlled postMessage bridge, giving servers a UI surface without shipping native code. Actionability angle: If you run an MCP server in production behind a load balancer, the stateless RC removes the sticky-session constraint — your server fleet can now scale horizontally without session affinity. Audit your server for server-side session state and migrate it to the client or an external store. Watch the MCP Apps extension for a server-rendered UI pattern that could replace custom prompt-injection UIs in your agent tooling. Listener hook: MCP just went stateless — the protocol that connects every agent to every tool can now scale horizontally without sticky sessions, and extensions are now a first-class ship mechanism.

[09:00] MCP July 2026 Release Candidate

The Model Context Protocol working group published the July 28, 2026 Release Candidate on June 8, 2026, marking the most significant architectural change in MCP's history. The core shift is from a stateful session model to a stateless transport with optional stateful applications layered on top. In the previous model, MCP clients maintained a session store on the server side — a sticky-session constraint that made horizontal scaling impossible without session affinity at the load balancer. The RC removes this by moving all session context into the request payload itself, so any MCP client can route to any server replica with no session store required.

Server-to-client requests are restructured. Previously, a server could push data to the client only through the sampling callback — a narrow, specialized path. The RC adds a general `server_request` primitive to the JSON-RPC layer, enabling servers to push prompts, resource updates, or tool results without a client poll. This is architecturally similar to how SSE (Server-Sent Events) works in HTTP — a server-initiated stream with client-side subscription.

The Extensions framework is now first-class. New capabilities ship as opt-in extensions with their own versioned namespace, stabilize in extension form, and only move into the core spec if and when they earn broad adoption. The MCP Apps extension (SEP-1865) lets servers ship interactive HTML interfaces rendered in sandboxed iframes with a controlled `postMessage` bridge — a server-rendered UI pattern that could replace custom prompt-injection UIs in agent tooling. The Tasks extension graduates from experimental to a named extension.

Three previously experimental features are deprecated under the new feature lifecycle policy (SEP-2577). Full JSON Schema 2020-12 validation for tools is now required rather than recommended.

Operator surfaces: MCP server implementors need to audit their code for server-side session state and migrate it to the client or an external store. MCP client hosts should update to handle the new `server_request` primitive. The Extensions framework means new capabilities will ship as opt-in additions rather than spec changes — watch extension versions as leading indicators of new MCP functionality.

What agents can now do that was previously impossible: scale MCP server infrastructure horizontally without sticky sessions; receive server-initiated pushes without polling; use server-rendered UI surfaces (MCP Apps) as interactive components within agent sessions.

[09:00] MCP July 2026 Release Candidate: stateless protocol, server-initiated requests, and the extensions framework

Nova The Model Context Protocol working group published the July 28, 2026 Release Candidate on June 8, 2026, marking the most significant architectural change in MCP's history. The core shift is from a stateful session model to a stateless transport with optional stateful applications layered on top. In the previous model, MCP clients maintained a session store on the server side. That was a sticky-session constraint that made horizontal scaling impossible without session affinity at the load balancer. Every request from a client had to route back to the same server that held its session state, which meant you could not put an MCP server fleet behind a standard load balancer and scale out. The RC removes this by moving all session context into the request payload itself. Any MCP client can now route to any server replica with no session store required. That is a fundamental change in how the protocol operates in production, and it is the change that every operator running MCP servers behind a load balancer has been waiting for.

Alloy Server-to-client requests are restructured. Previously, a server could push data to the client only through the sampling callback, which was a narrow, specialized path designed for one specific use case. The RC adds a general server-request primitive to the JSON-RPC layer, enabling servers to push prompts, resource updates, or tool results without a client poll. This is architecturally similar to how Server-Sent Events work in HTTP. A server-initiated stream with client-side subscription. The server does not wait for the client to ask. It sends the update when it has something to send. For agents that rely on real-time server state, this removes the polling loop that added latency and overhead.

Nova The Extensions framework is now first-class. New capabilities ship as opt-in extensions with their own versioned namespace, stabilize in extension form, and only move into the core spec if and when they earn broad adoption. This is a governance change as much as a technical change. It means the MCP spec is no longer the only vehicle for new functionality. Extensions can ship independently of the core spec cycle, which gives the ecosystem a faster path to deliver new capabilities. The MCP Apps extension, which is SEP-1865, lets servers ship interactive HTML interfaces rendered in sandboxed iframes with a controlled postMessage bridge. This is a server-rendered UI pattern that could replace custom prompt-injection user interfaces in agent tooling. Servers can author an HTML interface, ship it to the client, and the client renders it in a sandboxed iframe. The agent can interact with that interface without the client needing to understand the interface's logic. The Tasks extension graduates from experimental to a named extension, which means it has a stable interface and a defined behavior contract.

Alloy Three previously experimental features are deprecated under the new feature lifecycle policy, which is SEP-2577. Full JSON Schema 2020-12 validation for tools is now required rather than recommended, which means MCP tool implementations need to produce schema-compliant output or the client will reject them. The spec is stricter now, which is the right direction for a protocol that is being adopted in production environments where malformed tool responses can break agent sessions.

Nova The operator surfaces that change are the MCP server implementations. Server implementors need to audit their code for server-side session state and migrate it to the client or an external store. The stateless model means the server no longer holds per-client state between requests. If your server has any in-memory state that represents a client session, that state must move to the client side, encoded in the request payload, or to an external store like Redis. MCP client hosts should update to handle the new server-request primitive, which means handling server-initiated pushes that arrive without a client poll. The Extensions framework means new capabilities will ship as opt-in additions rather than spec changes. Watch extension versions as leading indicators of new MCP functionality. The extension namespace is versioned independently of the core spec, which means you can pin to a specific extension version without upgrading the core protocol.

Alloy What agents can now do that was previously impossible: scale MCP server infrastructure horizontally without sticky sessions, which means a standard load-balanced deployment with multiple server replicas is now a supported topology rather than a workaround. Receive server-initiated pushes without polling, which means agents can respond to server state changes in real time rather than waiting for the next polling interval. Use server-rendered UI surfaces as interactive components within agent sessions, which opens a new class of human-in-the-loop workflows where the server provides a structured interface that the agent navigates.
