[02:00] Release Readout do Agent Stack: Hermes Agent v0.21.6

O Hermes Agent v0.21.6 foi lançado em 8 de outubro como uma release de consolidação da Nous Research — aproximadamente 2.100 pull requests desde a v0.21.5 mesclados no primeiro tag Docker e Hermes Cloud cortado por um pipeline de release totalmente novo. Esse pipeline produz uma referência de tentativa única, uma imagem Docker testada, e um receipt tag na publicação. O Desktop, pacotes Termux e o build da Microsoft Store permanecem em suas versões atuais e serão movidos com o próximo release agrupado, então esta rodada é realmente direcionada a usuários de container e cloud.

O número principal é a escala da janela mesclada: 8.867 commits não-merge através de 8.342 arquivos alterados, aproximadamente 772.000 linhas adicionadas e 225.000 removidas, fechando 3.027 issues. Notas curadas para tudo isso aguardam até a v0.22.0, mas o post de release destaca alguns dos bits mais interessantes de propósito.

Para builders, as mudanças mais concretas incluem transcrição por streaming ao vivo enquanto você fala no CLI, TUI e Desktop (a flag stt.streaming), turnos de voz falados roteados para um modelo dedicado via auxiliary.voice_chat com raciocínio desligado por padrão, e plugins de terceiros agora rodando em um plugin host por perfil quando plugins.isolation está definido como "host" — significando que um plugin mal comportado não pode mais tocar sua configuração principal do Hermes. O Desktop picker agora fixa favoritos no topo, e provedores com rate limit informam tanto o motivo quanto até quando eles te bloqueiam.

Usuários de IA local obtêm suporte CUDA do llama.cpp no Linux x64 e arm64, com modelos locais listados diretamente sob hermes model. Há também uma saída hermes status primeiro com resumo usando flags --short ou --full, um seletor de escopo de diff do review-pane cobrindo Uncommitted, Branch e Last turn, keep-awake que rastreia o turno ativo, e avisos de cron quando a schedule store se torna não-gravável. Duas adições de segurança aparecem como prompts de aprovação: uma para uploads de credenciais, uma para caracteres Unicode invisíveis em comandos de terminal.

Os catálogos agora listam GPT-6.1 Sol e Claude Sonnet 5.5 junto com Haiku 5.5. Há muito mais na janela — dezenas de plugins da comunidade, uma configuração do Discord que valida o token do bot e imprime o link de convite, language packs em camadas plugáveis através de core, Desktop e TUI, e um fluxo de trabalho Kanban unificado — mas o post de release deliberadamente deixa essa lista para a v0.22.0.

Uma coisa para observar a seguir: a tag v0.22.0, que deve trazer os destaques curados e créditos completos de contribuidores para tudo desde a v0.21.0. Se você está planejando uma atualização maior, segurar até que essas notas cheguem é o movimento seguro.

[03:43] StepFun lista Step 5 Preview no OpenRouter para trabalho agentic

A StepFun surfou um novo modelo de preview flagship, o Step 5 Preview, listado no OpenRouter como o modelo flagship da StepFun para trabalho agentic. A arquitetura é um setup sparse Mixture-of-Experts, o que significa que apenas uma fração dos parâmetros totais se ativa em qualquer query: 27 bilhões de ativos de 600 bilhões totais. Essa proporção importa porque permite que o modelo carregue uma base de conhecimento enorme sem pagar custo total de inference em cada chamada. O comprimento de contexto fica em um milhão de tokens, então uma única sessão pode segurar uma base de código grande ou a memória de trabalho de um agente de longa duração. O listing está no OpenRouter, que roteia requests para o provedor subjacente, então builders podem testar através de uma única superfície de API. Como este é um modelo de preview, espere que ele mude conforme a StepFun itera — útil para prototipar loops de agentes agora, com a ressalva usual de que pesos e comportamento podem mudar antes de um release geral. Se você constrói agentes de codificação, isso vale um teste lado a lado contra seu default atual, mas fixe a versão do modelo e mantenha um fallback conectado enquanto ainda está em preview. Ele usa uma arquitetura sparse Mixture-of-Experts com 27B ativos e 600B totais de parâmetros, performa fortemente em engenharia de software, e suporta um comprimento de contexto de 1.000.000 de tokens. O modelo é listado pelo OpenRouter e é alcançável na página do modelo step-5-preview no OpenRouter.

[05:06] Google transforma Gemini em um agente de trabalho que aceita objetivos, não instruções

O Google usou seu evento Cloud em 8 de outubro para impulsionar o Gemini para o que chamou de era agentic, começando com negócios. O pitch do CEO Sundar Pichai foi escala: aproximadamente 1 bilhão de usuários mensais do Gemini, e cerca de 90 por cento das empresas da Fortune 100 no Gemini Enterprise. O novo agente lands primeiro lá porque, como Pichai colocou, é lá que os problemas mais difíceis de segurança e escala são resolvidos.

O que mudou mecanicamente: Thomas Kurian do Google Cloud disse que usuários podem entregar ao agente "objetivos, não apenas instruções." Ele planeja o trabalho, carrega habilidades customizadas, e conecta a sistemas internos incluindo Google Workspace, Microsoft 365, Slack, Jira, Confluence, Git, BigQuery, Databricks, Postgres e Snowflake. Anexos podem agrupar arquivos, pastas, ou project packs de arquivos e habilidades.

Modelos são selecionados por padrão, mas usuários podem sobrescrever, com o Claude da Anthropic como a primeira opção de terceiros, e modelos open source e privados prometidos para depois. Ferramentas andam no Model Context Protocol, então qualquer servidor MCP dentro ou fora da rede pode plugar.

O detalhe de persona é o mais concreto: o agente ganha sua própria conta Workspace — próprio email, próprio contexto, e uma trilha de auditoria atribuída ao agente. Ele lê organogramas, fusos horários, aprovadores e calendários, e você alcança ele por tag, email, share, ou grupo chat. Uma caixa de entrada de tarefas mostra seu raciocínio, os subagentes que ele delegou, as habilidades que carregou, e seu progresso.

Ele abre no iOS, Android, Windows, Mac, linha de comando, Workspace, Microsoft 365, ServiceNow e Slack. Testadores iniciais incluíram On, Shopify e PayPal; clientes enterprise nomeados incluem BNP Paribas, Merck, Orange Spain e Ulta Beauty. O Google também adicionou controles de gasto — orquestração multi-modelo, roteamento inteligente e caps em tempo real — então uma tarefa descontrolada não pode estourar um orçamento.

Observe a seguir: quando este agente se expande além do Gemini Enterprise, e se o seletor de modelo aparece em alguma API de desenvolvedor ao invés de apenas dentro da interface do consumidor.

[07:05] GitHub Copilot agora faz sandbox de seus próprios comandos na sua máquina

O GitHub Copilot agora pode envolver os comandos que executa no seu computador dentro de um sandbox local. O recurso está geralmente disponível a partir de 7 de outubro no Copilot CLI, no aplicativo Copilot e nas sessões do VS Code que usam o Agent Host.

O objetivo é permitir que um agente autônomo aja na sua máquina sem deixá-lo agir como você. Quando o Copilot dispara uma chamada de ferramenta, ela agora é executada sob uma política que você ou sua empresa define, e essa política pode manter a chamada longe da maior parte do sistema de arquivos, da internet aberta, da sua rede local, das credenciais do Git e das credenciais do GitHub CLI. Se o agente tentar fazer algo que a política proíbe, isso simplesmente não acontece.

Por baixo do capô, a aplicação é tratada pelo Microsoft eXecution Container, ou MXC, que traduz um arquivo de política em controles nativos do sistema operacional no Windows, macOS e Linux. As primitivas de sandbox parecem diferentes em cada plataforma, então uma política comum significa que desenvolvedores e equipes de segurança só precisam escrever as regras uma vez. A mesma política cobre ferramentas locais que o Copilot conecta, incluindo servidores MCP locais e servidores de linguagem onde essas integrações são suportadas, então a fronteira não se limita ao próprio agente. O isolamento de ferramentas é deliberadamente mantido separado da escolha do modelo, então as regras funcionam independentemente de qual modelo o Copilot está usando.

Para os desenvolvedores, a vantagem prática é a permissão para delegar mais responsabilidade a um agente em um projeto real sem entregar o seu notebook. Você define quais diretórios ele pode ler e escrever, quais hosts ele pode chamar e quais credenciais ele pode ver. Administradores de empresas podem ir além e exigir o sandbox através de configurações gerenciadas, com políticas que os desenvolvedores não podem enfraquecer. O GitHub está incluindo o recurso com o Copilot sem custo adicional.

Vale observar a seguir: quão agressivos os presets de política local padrão acabam sendo para fluxos de trabalho comuns em Python e Node, onde instalações de pacotes e servidores de desenvolvimento local desejam acesso bastante amplo.

[09:05] GitHub Copilot CLI agora pode encontrar modelos locais do Ollama

O GitHub Copilot CLI agora detecta os modelos locais já em execução na sua máquina. A partir da versão 1.0.94-0, o comando /model no Copilot CLI listará modelos suportados de uma instância Ollama em execução ao lado das suas opções configuradas e dos modelos em nuvem que o GitHub fornece.

O fluxo é deliberadamente não destrutivo. A descoberta não adiciona nada automaticamente. Você escolhe um modelo da lista, revisa seu provedor e endpoint, e então escolhe "Adicionar e usar para esta sessão" ou "Adicionar sem trocar". Uma vez confirmado, o modelo funciona na sessão atual, sem necessidade de reiniciar o CLI.

Dois guardrails importantes são descritos. Primeiro, isso é apenas descoberta: o Ollama e o modelo já devem estar instalados. O CLI não instalará um runtime ou puxará pesos para você. O modelo também precisa suportar tool calling e streaming, então nem toda tag do Ollama aparecerá. Segundo, quando algo dá errado, digamos que o Ollama não está acessível, a falha aparece diretamente no seletor com uma explicação, então você sabe o que corrigir.

O recurso espelha a experiência de provedor do aplicativo GitHub Copilot, onde você adiciona provedores suportados em Configurações > Provedores de modelos. Uma seleção local no CLI, porém, não ativa o modo offline nem silencia a telemetria do GitHub. O modo offline ainda é uma escolha explícita, definida com COPILOT_OFFLINE=true, e mesmo assim um provedor remoto ainda pode receber prompts e contexto de código pela rede, vale saber se você está lidando com código sensível.

O GitHub também anunciou um recurso de roteamento inteligente para modelos locais, com detalhes no blog Microsoft Command Line e disponibilidade a seguir. Por agora, o movimento prático é simples: mantenha o Ollama em execução, abra o Copilot CLI e digite /model; suas opções locais estarão lá.

[10:49] Perplexity lança um embedder pequeno e um grande

A Perplexity lançou o pplx-embed-v2-late, um novo modelo de embedding que vem em dois tamanhos. O menor tem 600 milhões de parâmetros, construído para rodar em dispositivos de borda como laptops e celulares. O maior tem 9 bilhões de parâmetros, aimed at building high-quality search indexes. Ambos são licenciados sob MIT, meaning anyone can download them, run them locally, and modify them without paying Perplexity.

O número principal é 92,4% no MADQA, pontuado pela variante de 9B. Isso o coloca na conversa com outros embedders de primeiro nível. O outro lado é a pontuação mais fraca: 61,2% no ViDoRe v3 Markdown, o que sugere que o modelo é menos confiável ao recuperar de documentos no estilo Markdown. Se sua stack é pesada em Markdown ou conteúdo de documentos renderizados, você vai querer testar antes de apostar nisso em produção.

O apelo prático é a licença de auto-hospedagem combinada com credenciais de borda. Um embedder de 600 milhões de parâmetros é pequeno o suficiente para bundlar dentro de um aplicativo desktop ou móvel, abrindo a porta para busca semântica, deduplicação e recursos de similaridade que funcionam sem uma chamada de rede. O modelo de 9B se encaixa em equipes que precisam de máxima qualidade de recuperação em infraestrutura que controlam.

A coisa a se observar é como isso performará em corpora de conteúdo misto, já que a fraqueza em Markdown importa mais para stacks de recuperação do mundo real. Embeddings auto-hospedados têm ficado silenciosamente melhores, e este lançamento é um passo notável nessa direção.

[12:12] EmbeddingGemma 2 do Google DeepMind coloca texto, imagem, áudio e vídeo em um único vetor de 768 dimensões

O Google DeepMind open-sourced o EmbeddingGemma 2, um modelo de embedding de 740 milhões de parâmetros que transforma texto, código, imagens, vídeo e áudio em um único vetor de 768 dimensões. A card o descreve como um modelo de embedding multimodal open-source construído sobre os avanços arquitetônicos do Gemma 4, shippando sob Apache 2.0, e o Unsloth já publicou um build GGUF para inferência local. Diferentemente de um modelo generativo, o EmbeddingGemma 2 é projetado para busca semântica, recuperação, classificação e clustering. Seu backbone de texto de 270 milhões de parâmetros — um transformer de 130M mais um embedder de 140M — pode rodar sozinho para cargas de trabalho apenas de texto. Os encoders de visão (170M) e áudio (300M) são modulares, então um desenvolvedor fazendo busca de texto e imagem pode descartar o caminho de áudio e encolher a pegada efetiva para 440M parâmetros. As quatro modalidades compartilham uma janela de contexto de 8.192 tokens, e as entradas podem ser intercaladas usando tokens de espaço reservado como <|image|>, <|video|> e <|audio|>. A card também documenta o Matryoshka Representation Learning, que permite que a saída de 768 dimensões seja truncada para 512, 256 ou 128 dimensões e renormalizada. Em 256d, a pontuação MTEB-multilingual só cai de 61,36 para 60,41 — aproximadamente um corte de armazenamento de 3x com perda mínima de qualidade. Em 128d, os benchmarks multimodais degradam mais acentuadamente, então a card recomenda validar contra sua própria carga de trabalho. Dois avisos práticos se destacam. Primeiro, rode a inferência em bfloat16 ou float32; em float16 o modelo retorna NaN ou embeddings silenciosamente degradados sem nenhum erro levantado. O EmbeddingGemma 2 é um sucessor do EmbeddingGemma 1 e alega aproximadamente uma melhoria relativa de 14% em tarefas de embedding de código. O EmbeddingGemma 2 shippa sob Apache 2.0 e carrega via sentence-transformers com o id do modelo google/embeddinggemma-2, com um build GGUF do Unsloth também disponível. O modelo mapeia texto, código, imagens, vídeo e áudio em um espaço de embedding unificado de 768 dimensões, com encoders de visão e áudio modulares opcionais. O publicador relata que no MTEB-code v1 o EmbeddingGemma 2 pontua 78,68 versus 68,76 do EmbeddingGemma 1, enquanto o MTEB-multilingual v2 é essencialmente plano em 61,36 versus 61,15. A card do modelo adverte que a inferência em float16 retorna NaN ou embeddings silenciosamente degradados e que truncar para 128 dimensões degrada significativamente a qualidade multimodal.

[14:19] PivotOPD da NVIDIA Treina Agentes para Pegarem Seus Próprios Erros Iniciais

Pesquisadores da NVIDIA introduziram o PivotOPD, uma receita de treinamento focada em um dos modos de falha mais irritantes em agentes AI multi-turn: travar em uma escolha errada no início e depois nunca se recuperar dela.

O método funciona através de destilação on-policy, que é uma forma elegante de dizer que o agente aprende de trajetórias que ele próprio produziu durante seus próprios treinos, em vez de aprender de uma biblioteca fixa de demonstrações de especialistas. O processo de treinamento aumenta especificamente o peso dos erros decisivos, aquelas jogadas iniciais onde o agente tomou uma decisão que moldou tudo o que veio depois, para que o modelo pratique reconhecer e corrigi-los em tempo real.

Nos testes frente a frente, o PivotOPD alcançou a melhor pontuação média em três benchmarks de agentes contra 13 configurações alternativas de treinamento. A perspectiva importa porque benchmarks de agentes tendem a ser impiedosos: uma única decisão ruim no início se propaga pelo resto da execução, então um método que mira especificamente essas jogadas decisivas está atacando o modo de falha diretamente.

A pesquisa é de uma equipe da NVIDIA e surgiu através do MarkTechPost em 8 de outubro. O que vale acompanhar é se o código de treinamento chega a equipes externas, já que o comportamento de recuperação só se torna útil para outros desenvolvedores se conseguirem reproduzi-lo em suas próprias pilhas de agente. Até lá, o aprendizado prático é conceitual: a recuperação de erros iniciais é uma propriedade treinável, não algo que os desenvolvedores precisam aceitar como uma limitação do modelo base.

[15:45] Resumo de pesquisa: Mundos Feitos de Código, Agentes Que Passam Notas Adiante

Pesquisadores do Mirros Lab estão treinando agentes de IA dentro de mundos escritos como código e observados através de um renderizador de vídeo neural aprendido. Regras, objetos e objetivos existem em um programa executável, e o renderizador transforma essa geometria em quadros de câmera que o agente vê em tempo real, a mais de 30 quadros por segundo em 480 por 832 em um H100. Agentes pré-treinados jogam os mundos, e após cada rodada eles anotam o que funcionou em um arquivo de notas que alimenta os agentes da próxima rodada. Ao longo de quatro rodadas, uma carregadeira de rodas foi de limpar pedras para também entregar uma em um bunker e estacionar com 31 segundos restantes; uma troca de ponte de faixa única ensinou os agentes a ceder na curva e se re-centralizar sem esperar. O mesmo loop rodou em esconde-esconde, pastoreio de ovelhas e um exercício de engajamento com cachorro de 60 segundos, com cada rodada continuando de onde o playbook anterior parou. Por que importa: ambientes que combinam código inspecionável, renderização em tempo real e anotações de rodada em rodada poderiam dar aos pesquisadores uma forma mais rápida de desenvolver habilidades de agente em navegação, manipulação e uso de ferramentas em uma configuração compartilhada.

[16:52] OpenAI Compartilha Avanços Matemáticos com Provas Formais no GitHub

A OpenAI publicou novos resultados sobre problemas abertos em matemática em 6 de outubro, vindos de um modelo de fronteira interno. O que torna o lançamento incomum é que a empresa não apenas descreveu o que o modelo encontrou. Ela postou formalizações de provas em Lean e os detalhes da pesquisa de apoio no GitHub para que o trabalho possa ser inspecionado e verificado.

Lean é um assistente de prova formal, um ambiente estilo programação para matemática onde cada passo em um argumento tem que seguir regras que o sistema impõe. Quando uma prova é formalizada em Lean, um humano ou uma IA pode executá-la através da ferramenta e confirmar que a conclusão realmente segue dos axiomas. Isso importa porque artigos de matemática, até mesmo os celebrados, podem esconder lacunas sutis que só aparecem anos depois. Uma prova verificada pelo Lean é o mais perto que o campo chega de uma transcrição do raciocínio.

Para o lançamento da OpenAI, qualquer pessoa que conheça Lean pode clonar o repositório, ler os scripts de prova e ver exatamente quais problemas o modelo abordou e como os argumentos foram construídos. Pesquisadores podem comparar as formalizações com a versão em prosa para ver onde o modelo está sendo preciso e onde pode estar simplificando demais.

Para desenvolvedores e engenheiros de IA, o sinal interessante é que laboratórios de fronteira estão tratando verificação formal como um produto de pesquisa de primeira classe. O mesmo fluxo de trabalho, deixando um modelo propor uma prova, formalizá-la e então verificá-la, está começando a parecer um padrão generalizável para qualquer tarefa de raciocínio de alto risco onde você quer mais do que uma resposta que parece plausível.

A thread do Hacker News sobre o lançamento recebeu mais de mil e trezentos votos positivos, refletindo forte interesse das comunidades de matemática e IA. Vale acompanhar a seguir: se grupos independentes reproduzem as provas, e se a OpenAI libera mais do comportamento subjacente do modelo para que outros possam testar a abordagem em problemas que o laboratório não escolheu.

[18:46] Cactus Compute Lança Reconhecimento de Voz de 17 Megabytes que Roda Localmente

A Cactus Compute lançou o Whistle, um modelo aberto de reconhecimento de voz que cabe em 16,9 MB e roda no dispositivo através de seu motor em C++ sem nenhuma dependência externa. O modelo processa até 30 segundos de áudio mono de 16 kHz em inglês, alemão, francês, espanhol, italiano, holandês e polonês, com detecção automática de idioma emitindo o resultado como um token em vez de devolvê-lo fora da banda. A latência do primeiro token é de 5,9 ms com cinco segundos de áudio, 11,1 ms com dez segundos e 36,3 ms com trinta segundos em um Apple M4 Pro. O Whistle supera o Whisper base no LibriSpeech test-clean e test-other, SPGISpeech, Earnings-22 e na média multilíngue do FLEURS enquanto requer um nono do espaço em disco a 145,3 MB. A arquitetura espelha o Needle com oito blocos codificadores de Simple Attention e oito blocos decodificadores de Laddered Simple Attention com largura 512, adicionando cross-attention com portão por camada do decodificador que lê a saída do codificador uma vez no carregamento do clip e faz cache através da pesquisa de cinco feixes. O mesmo binário que carrega o Needle para tarefas de texto pode carregar o Whistle junto com ele, e needle_complete transcreve áudio diretamente em chamadas de ferramentas, retornando um objeto JSON com function_calls, audio_text e timing sem expor uma transcrição bruta ao chamador. Binários pré-construídos são distribuídos para dezessete alvos abrangendo macOS, Linux, Android, iOS, watchOS, Windows em ARM, RISC-V, MIPS, o navegador e um componente WASI. Os pesos estão no Hugging Face, o motor está no Cactus-Compute/needle3 e o código-fonte está no GitHub.

[21:45] Resumo de pesquisa: Um Motor de Servimento Que Alterna Entre Modelos no Meio da Resposta

TokenRouter é um motor de serviço de um artigo do NeurIPS 2026 que permite que um modelo pequeno e um grande colaborem em uma única resposta, alternando token por token. Resultado principal: no benchmark R2R, o motor alcança 372,48 tokens por segundo versus 134,90 da configuração oficial, cerca de 2,76 vezes mais rápido.

O sistema mantém o KV cache de cada modelo localmente e apenas envia os sufixos de tokens mais o estado de roteamento entre os subservidores. Um agendador agrupa requisições de ambos os modelos e usa uma cadeia de Markov em tempo discreto para escolher um limiar de agrupamento atrasado que maximiza os tokens comprometidos por unidade de tempo. Os grafos CUDA e a execução assíncrona permitem que o modelo pequeno continue decodificando enquanto o modelo grande é executado em paralelo.

Entre pares Qwen3 em um host com oito A100, os ganhos variam de 1,99 vezes (4B sobre 8B) a 3,21 vezes (0.6B sobre 8B). Na concorrência 16, o motor entrega 630,57 tokens por segundo no agregado com 39,41 por usuário. A implantação em múltiplos nós sobre RoCE de 3.7 GB/s adiciona uma sobrecarga modesta.

Para construtores, um modelo front-end barato pode entregar tokens difíceis para um parceiro maior sem perder throughput, desde que a implantação inclua o agendador e a contabilidade de KV por modelo.

[22:54] Gemini Agent do Google Cloud: Um Prompt para Trabalho Empresarial

O Google Cloud lançou o agente Gemini, uma única interface hospedada na nuvem posicionada como uma superfície universal para trabalho empresarial. O anúncio o descreve como respondendo perguntas, fazendo trabalho de conhecimento, criando mídia e escrevendo e executando código, tudo a partir de uma caixa de prompt e uma API.

A consolidação é o argumento principal. Em vez de rotear uma requisição de pesquisa para um sistema, uma tarefa de documento para outro e execução de código para um ambiente de desenvolvimento, o agente Gemini expõe uma superfície de prompt para tudo. Equipes empresariais que já armazenam dados dentro do Google Cloud obtienen um alvo mais simples para seus fluxos de trabalho. Desenvolvedores acessam essas variadas capacidades através do mesmo endpoint de API em vez de costurar integrações separadas.

Para construtores, a vitória prática é a redução da sobrecarga de orquestração dentro do ecossistema Google Cloud, uma integração substituindo várias. A questão aberta interessante é quão bem uma superfície de prompt realmente se sustenta em tipos de tarefas tão diferentes quanto gerar mídia e executar código. A prova estará em quão limpiamente a mesma conversa pode fluir de uma requisição de pesquisa para uma requisição de código sem perder contexto ou qualidade. Os clientes que estão testando agora serão os que nos dirão se a superfície universal entrega o que promete.
